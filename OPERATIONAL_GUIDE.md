# GeoShield Operational Major-Project Guide

GeoShield is designed to run as a complete software monitoring platform, not only as a presentation simulator. The simulator remains available for controlled testing, while real gateway readings use a separate authenticated ingestion path and are tagged independently in the database.

> The software pipeline can accept real sensor measurements. Operational landslide-warning accuracy still requires calibrated field hardware, prospective data collection, threshold calibration, and independent validation.

## 1. Recommended full-stack runtime

For the most production-like academic setup use PostgreSQL:

1. Copy the template:
   ```bash
   cp .env.production.example .env.production
   ```
2. Replace every placeholder secret in `.env.production`.
3. Start the application and PostgreSQL:
   ```bash
   docker compose --env-file .env.production -f docker-compose.production.yml up --build
   ```
4. Open:
   ```text
   http://127.0.0.1:8000
   ```
5. Check readiness:
   ```text
   GET http://127.0.0.1:8000/api/health/ready
   ```

The application applies Alembic migrations automatically and refuses to report ready if its database is unavailable.

## 2. Persistent authentication

The production profile disables repository demo users.

On first startup, the configured `GEOSHIELD_ADMIN_EMAIL` and `GEOSHIELD_ADMIN_PASSWORD` bootstrap a persistent administrator in the database. After that, administrators can create additional accounts from **Administration** in the web UI.

Supported roles:

- `admin`
- `district_admin`
- `field_officer`
- `citizen`

Accounts can be disabled without deleting their history.

## 3. Monitoring-station provisioning

Administrators can provision stations from **Administration → Provision monitoring station**.

A station contains:

- stable station ID
- latitude/longitude
- state, district and locality
- elevation and slope
- soil type
- vegetation cover
- active/inactive status

This means a production database does not need to depend permanently on the bundled 20 reference stations.

For a clean real-input setup set:

```text
AUTO_SEED_REFERENCE_DATA=false
```

For an academic environment that also needs historical/reference charts, keep it true.

## 4. Real sensor/gateway ingestion

Enable ingestion:

```text
SENSOR_INGEST_ENABLED=true
SENSOR_INGEST_API_KEY=<long random secret>
```

A gateway sends:

```text
POST /api/sensors/stations/{station_id}/readings
X-GeoShield-Sensor-Key: <configured key>
Content-Type: application/json
```

Example payload:

```json
{
  "external_id": "gateway-node-12-0001042",
  "rainfall_mm": 82.4,
  "soil_moisture": 78.2,
  "soil_temperature": 23.8,
  "ground_displacement": 6.3,
  "tilt_angle_x": 2.1,
  "tilt_angle_y": 1.7,
  "pore_water_pressure": 68.0,
  "vibration_level": 12.0,
  "observed_at": "2026-09-19T10:30:00+05:30"
}
```

GeoShield then performs the complete pipeline:

```text
gateway observation
    ↓
input validation + API-key authentication
    ↓
persistent SensorReading
    ↓
ML risk inference
    ↓
persistent RiskAssessment
    ↓
moderate/high/critical decision
    ↓
persistent alert
    ↓
dashboard / station / alert workflow
```

`external_id` provides idempotency: re-sending the same gateway event will not duplicate the reading.

## 5. Gateway helper

A standard-library Python client is included:

```bash
python tools/send_sensor_reading.py \
  --server http://127.0.0.1:8000 \
  --station NER-101 \
  --api-key "<sensor-key>" \
  --rainfall 82.4 \
  --soil-moisture 78.2 \
  --displacement 6.3 \
  --tilt-x 2.1 \
  --tilt-y 1.7 \
  --pore-pressure 68
```

The same HTTP contract can be called by a Raspberry Pi, ESP32 gateway, LoRaWAN network server, cellular gateway, or another telemetry service.

## 6. Data provenance

Sensor readings are tagged by origin.

Typical values:

- `sensor_gateway` — authenticated external observation
- `simulation` — controlled scenario generated by the simulator
- `seeded_reference` — bundled reproducible reference/history data
- `legacy` / `unknown` — older database data created before provenance tracking

Simulation reset only removes simulation-tagged data. It does not erase gateway readings.

## 7. Database options

### Local development

SQLite remains supported for quick development and single-machine use.

### Full major-project stack

PostgreSQL is recommended for the complete multi-user persistent configuration. GitHub Actions creates a fresh PostgreSQL instance, applies all migrations, and runs the operational-core tests against it.

## 8. Health model

Two health endpoints have different meanings:

- `/api/health` — API process is alive.
- `/api/health/ready` — application is ready and can query its database.

The Docker health check uses the readiness endpoint.

## 9. What the simulator is for

The simulator is not the main data source. It is retained as a controlled test facility for:

- testing critical/high-risk workflows
- verifying RBAC
- checking alert generation
- demonstrating behavior when field hardware is unavailable
- regression testing

Simulator readings and alerts are explicitly labelled and kept separate from external sensor observations.

The repository CI verifies:

- complete backend regression suite
- Docker production image build
- real container boot and HTTP smoke flows
- production authentication behavior
- Alembic migrations
- PostgreSQL operational tests
- persistent user lifecycle
- station provisioning
- authenticated sensor ingestion and idempotency
- ML inference triggered by sensor ingestion
- browser-level citizen-report/admin-review workflow
- Python dependency + static security audit
- Windows offline startup workflow
- Capacitor Android APK build and debug transport policy
- bundled Electron backend, packaged Windows app and NSIS installer
- destructive PostgreSQL backup/restore recovery drill

A green CI run verifies these tested software paths. It does not certify geological prediction performance in the field.

## 11. Field-deployment extension

For a physical deployment, a reasonable communication chain is:

```text
rain gauge / soil-moisture / inclinometer / pore-pressure sensors
        ↓
microcontroller / edge node
        ↓
LoRa / LoRaWAN / RS-485 / local wireless link
        ↓
gateway with buffering
        ↓
cellular / broadband backhaul
        ↓
GeoShield sensor-ingestion API
        ↓
ML + database + alert workflow
```

The gateway should buffer timestamped readings during network loss and resend them later with stable `external_id` values. GeoShield's idempotency prevents retransmissions from creating duplicate observations.

## 12. Meaning of “fully working”

For this repository, **fully working software** means that the implemented application layers run together end-to-end: authentication, persistent database, station management, ingestion, prediction, alerts, web UI, migrations, Docker and automated verification.

It does **not** mean that the project is already a government-certified early-warning system or that the ML model can guarantee real-world landslide prediction without field validation.


## 13. Frozen academic release

The final-year project baseline is **v1.0.0**. Release architecture, verification
evidence, security boundaries and field-validation limitations are documented in
[docs/FINAL_PROJECT_FREEZE.md](docs/FINAL_PROJECT_FREEZE.md).

version rather than changing the frozen academic baseline.
